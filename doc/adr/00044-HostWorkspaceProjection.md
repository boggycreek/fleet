# 00044. Host Workspace Projection

## Context

[ADR 00005](00005-PersistedHomeVolumeAcrossRecreation.md) established named Podman volumes (`sndbx-agent-<name>-home`) mounted to `/home/agent` for persistent fleet sandboxes. This pattern isolates agent data within the container engine's storage pool, which is ideal for autonomous fleet workers checking out code from local Forgejo repositories.

However, when an operator pairs with an interactive coding agent on an existing project located on the physical workstation, storing files inside an isolated named volume introduces severe friction:
- Code must be artificially synchronized or pushed/pulled through git remotes between host and container.
- Host desktop editors (VS Code, JetBrains, Sublime) cannot access or monitor files directly on disk.

Conversely, naively bind-mounting the host's working directory into a standard rootless container causes permission and ownership issues: files created by the in-container user (UID 1000) are mapped to arbitrary unprivileged subuids on the host, preventing the operator from modifying or committing them from their host terminal.

---

## Decision (What)

We establish **Host Workspace Projection** for interactive host-connected agent containers:

1. **Direct Workspace Mount**: The operator's current working directory (`pwd` or explicit `--pwd <path>`) is mounted directly to the container's workspace path using the shared SELinux volume flag (`:z`):
   ```
   -v "${HOST_WORKSPACE_PATH}:/home/agent/workspace:z"
   ```
   Using lowercase `:z` ensures that host desktop editors, compilers, and host git commands continue to have read/write access without being locked out by private container MCS labels (`:Z`).
2. **User Namespace Mapping (`keep-id`)**: The container executes with explicit user namespace preservation:
   ```
   --userns=keep-id:uid=1000,gid=1000
   ```
   This maps the container's internal `agent` user (UID/GID 1000) directly to the physical operator's host UID and GID.
3. **Preserved File Ownership**: All files, directories, compiled artifacts, and git checkouts created by the agent container on disk remain owned by the physical host user with exact native host permissions.
4. **Isolated Home Volume Persistence**: In containerized host mode, the agent retains its dedicated named volume (`sndbx-agent-<name>-home`) mounted to `/home/agent:z` ([ADR 00005](00005-PersistedHomeVolumeAcrossRecreation.md)). This stores agent identity, backplane profile credentials, tool settings, and memories across container lifecycles without leaking or polluting the operator's physical host `$HOME`. The projected project directory is mounted strictly inside `/home/agent/workspace`.
5. **Lifecycle Independence**: Deprovisioning or recreating the agent container (`clean` / `retire`) destroys the container and internal home volume, but strictly preserves the physical host workspace directory without modification.

Accepted.

## Consequences

### Positive
- **Zero Permission Drift**: Operators can seamlessly edit, compile, or commit files generated by the agent without encountering permission denied or subuid ownership errors.
- **Immediate Host Sync**: Changes made by the containerized agent appear instantaneously in the operator's host IDE and shell.
- **Clean Workspace Boundary**: Confines container writes to the mounted project directory, leaving the rest of the host filesystem protected.

### Negative / Trade-offs
- **Host Path Dependency**: If the host project directory is moved or deleted, the container mount will fail on next invocation until reconfigured.
